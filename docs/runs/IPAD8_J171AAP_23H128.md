# iPad 8 (`j171aap`) on iPadOS 26.7.2 `23H128`

Experimental. On a real iPad 8 Wi-Fi the CFW restore, SSHRD and provisioning
work; the stock 23H128 iBEC refuses the normal boot, and the
`ibec-allow-duplicate-trust-cache` plan below is the fix for that. Every `fw`
command needs `--experimental`. Read
[the 23H30 notes](IPAD8_J171AAP_23H30.md) first; this build is its point
update and inherits every open item listed there.

Source: `iPad_10.2_2020_26.7.2_23H128_Restore.ipsw` (iPad11,6 / iPad11,7,
j171aap / j172aap). Kernel fingerprint
`xnu-12377.162.13.701.45~1/RELEASE_ARM64_T8020` (23H30:
`xnu-12377.162.13.700.38~2`), so it needs its own kernel profile.

## Profiles added

| Layer | Id |
| --- | --- |
| Kernel | `ios26-23H128-j171aap`, same variants and omissions as 23H30 |
| Workflow | `ipad11,6-j171aap-23H128`, same boot plan as 23H30 |

`KernelTaskAccessResolver` now names both reviewed kernel profiles instead of
23H30 alone, and `boot_artifacts.py` applies its task-access record check to
both workflow profiles.

The ACM roster reuses `ios26-23H30-acm-v1`: all 25 masked shapes match a
distinct function on 23H128 and the resolver's uniqueness checks still run.
If a later build needs any shape changed, give it its own variant rather than
editing this one.

## Comparison against 23H30

Every plan was resolved on 23H128 and compared against the 23H30 exact-build
fixtures by record id, original bytes and replacement bytes.

| Plan | Records | Same ids | Bytes that differ |
| --- | --- | --- | --- |
| `kernel ppl-trust-cache` | 1 | yes | none |
| `kernel credential-manager` | 50 | yes | none |
| `kernel task-access` | 15 | yes | none |
| `kernel sandbox-public` | 11 | yes | `vnode-check-exec.target` |
| `kernel boot-public` | 118 | yes | 8, below |
| `kernel boot-jit` | 138 | yes | the same 8 |
| `iboot ibec-restore` | 6 | yes | `ibss.boot-args.add` |
| `userland mobileactivationd` | 5 | yes | none, same offsets |
| `userland asr` | 1 | yes | none, same offsets |

Kernel records move by one of a few constant deltas (0x4140 to 0x8ef8). The
differing originals are all position-dependent fields, not changed logic:

- `kernel.debugger.result`, `kernel.amfi.developer-mode.result`,
  `selector7.12`, `selector7.19`: an `ADRP` whose page immediate changed.
- `kernel.amfi.dyld-policy.0`, `kernel.aks.external-method.log-call`: a `BL`
  whose displacement changed.
- `selector7.13`: `LDR X8, [X8, #0x1f0]` became `#0x330`, the low half of an
  ADRP/LDR pair. The shim overwrites it either way.
- `kernel.sandbox.vnode-check-exec.target`: the policy-table slot and the allow
  stub it is retargeted to both moved by the same 0x7d40.
- `ibss.boot-args.add`: the boot-args string cave moved by 0x140; the iBEC code
  itself resolves at the same offsets as 23H30.

`survey` on the extracted firmware matches 23H30: 21 plans resolve, and the
four without a candidate (`sandbox`, `boot`, `ibss-skip-display-init`,
`ibec-ignore-pinot-failure`) also have none on 23H30.

## Device fixes

The tweaks.list helpers and dylibs (`newterm-login`, `icleaner-launch`,
`l8rootapps`, `l8files`, `l8vpn-issue`, `eligibility`, `eligibility-persist`)
and `fw tweaks` now accept `23H128` as well as `23H30`. They locate functions
through `dlsym` and Objective-C selector lookups that fail closed when missing,
with no build-specific offsets, but **none of them has run on 23H128**. Watch
for: Files "On My iPad" missing, Karing VPN not connecting, AltStore eligibility
not sticking, NewTerm root login failing. Each fix has a marker and can be
turned off with `liter8_tweaks.py disable <name>`.

Build them with an iPhoneOS 16.5 SDK, for example
`LITER8_IOS_SDK=~/theos/sdks/iPhoneOS16.5.sdk ./build_tweaks.sh`: that builds
all eleven components and stages 20 files and 8 switches, and every staged
helper with a build guard carries both `23H30` and `23H128`. Xcode's iPhoneOS
27.0 SDK cannot build `rootappfix/l8rootapps.m` (its `xpc_object_t` typedef
clashes with the SDK's), with or without these edits.

## Normal boot: the 26.7.2 iBEC refuses the duplicate trust cache

**Symptom.** `fw boot` sends the whole chain, the iPad shows the Apple logo on
the blue iBEC background and stays there, still in Recovery Mode (USB PID
0x1281). The kernel never starts: the Data volume has no unified log, crash
report or `jbboot.log`. SSHRD on the same iBEC boots normally.

**What was ruled out on hardware** (tethered RAM boots, nothing written):

| Change to the normal boot set | Result |
| --- | --- |
| unpatched 23H128 kernel instead of `boot-jit` | still Recovery |
| stock DeviceTree (same iBEC session) | still Recovery |
| 23H30 iBSS/iBEC, everything else 23H128 | **boots** to the UI |

The 23H128 images are byte-identical to what the pre-merge iPad 8 branch
(`claude/quirky-meitner-fjokhj`) produces from the same inputs: kernel
(`boot-jit`, `boot-public`, `restore`), iBSS, iBEC, DeviceTree, IMG4 wrapping
and LZFSE (0x891) compression. The merge did not change the boot set.

**Cause** (static, 23H128 iBEC, file offsets of the raw payload):

- `0xb0ba0`: when no RestoreTrustCache is loaded, iBoot loads the
  StaticTrustCache from storage (`0xb0990`, type `trst`). Called from the
  kernel load path at `0x1248` (function `0x1078`, the `rkrn` loader).
- `0xb0704`: the add routine. New in 26.7.2: before adding, it walks the
  loaded trust caches (`ldr w8,[x0,#0x68]; cmp w8,w20; b.eq 0xb0934` at
  `0xb07dc`) and fails with `0x400d000c` when the type is already present.
- Liter8 has already sent the same StaticTrustCache with `firmware`, so the
  storage load is the second `trst`, the add fails and `bootx` returns.
- 26.7.1 has no such check (the resolver finds no candidate in 23H30 iBEC)
  and simply holds both copies. SSHRD sends RestoreTrustCache, which
  suppresses the storage load, so it never reaches the check.

**Fix.** `ibec-allow-duplicate-trust-cache` (`IBECAllowDuplicateTrustCacheResolver`)
replaces that `B.EQ` with `NOP`: one record, `0xb07e4 800a0054 -> 1f2003d5`.
It requires the `'rtsc'` type check, the load/compare loop on the incoming
type register and a failure target that builds 0x400d000c and returns -1, and
refuses zero or several candidates. The 23H128 profile selects it through the
new `DeviceBootPlan.normalIBECAdditionalPlans`, applied to the normal-boot
iBEC only, after `ibss-normal`; SSHRD and every other profile are unchanged.
The resulting iBEC differs from stock only in the validate, boot-args and this
one word. Fixture: `fixtures/23H128/j171aap/ibec-trust-cache-j171aap-23H128.json`.

What this patch does at runtime is what the 23H30 iBoot does, and that
configuration booted the 23H128 system. **The patched 23H128 iBEC itself has
not been booted yet**: the next `fw get-boot` + `fw boot` is that test. If it
stays in Recovery, the fallback measured above is the 23H30 bootloader.

## SIGKILL for binaries with debug entitlements

**Symptom.** Over SSH an ad-hoc binary runs, the same binary signed with
`get-task-allow` or `task_for_pid-allow` exits 137 (SIGKILL) at exec with no
AMFI or kernel log line. `security.mac.amfi.developer_mode_status` is 1. 23H30
had the same limit: Sileo and launchctl were re-signed without those
entitlements to work around it.

Measured on iPad11,6 / 23H128 (`hello` probe, root and mobile, `/var/jb`,
`/var/mobile`, `/var/tmp`):

| Signature | Result |
| --- | --- |
| `ldid -S`, `codesign -s -`, `platform-application`, arm64e | runs |
| `ldid -S` + `get-task-allow` | SIGKILL |
| `ldid -S` + `task_for_pid-allow` | SIGKILL |
| clang/Xcode linker signature only (`linker-signed`) | SIGKILL, not fixed here |
| no signature | SIGKILL, expected |

**Cause.** PPL validates every code directory through a chain of checks
(caller `0x2ba2e58` on 23H128). One of them, `0x32560bc`, is the only function
that references `task_for_pid-allow`; for trust level above 7 (all ad-hoc code
under the PPL trust-cache patch is level 9) it refuses `get-task-allow`,
`com.apple.private.cs.debugger`, `com.apple.system-task-ports.control` and
`task_for_pid-allow` unless PPL's own developer-mode byte is set
(`LDAPRB` + `TBNZ #0`). AMFI's developer-mode accessor is forced by the boot
plans; the PPL byte is not.

**Fix.** `kernel ppl-debug-entitlements` (`KernelPPLDebugEntitlementsResolver`)
turns that `TBNZ` into `B` to the same `MOV W0,#1` return: one record,
`0x32560fc e80a0037 -> 57000014` on 23H128 and `0x324e0fc` on 23H30 (the
function is shape-identical). It is part of the `kernel-codesign-invalid`
opt-in, so `boot-jit` grows from 138 to 139 records on both iPad profiles and
no other profile changes. **Not yet booted**: the next `fw boot` is the test;
`/var/jb/tmp/l8probe/hello.get-task-allow` and `hello.task_for_pid-allow` are
left on the device for it.

## Developer Mode: really on, not only reported on

**Symptom.** Hardware breakpoints do not fire, although
`security.mac.amfi.developer_mode_status` is 1.

**Cause** (23H128 file offsets; 23H30 is shape-identical at `0x19c7d24`):

- The boot plans force `developer_mode_state()` (`0x2f56450`) to return 1.
  That is the only thing behind the sysctl.
- The mode itself is a PPL byte (`0x3478640`) written only by the PPL toggle,
  call 100 (`0x2a16b1c` -> handler `0x3253ba0`), which `enable_developer_mode`
  (`0x2f56440`, `MOV W0,#1`) and `disable_developer_mode` (`0x2f56448`) reach.
- AMFI's boot decision (`0x19cf734`) disables in two places: directly when the
  mobile-obliteration status cannot be read (`0x19cf998`), and through its
  disable wrapper (`0x19d0118`, from `0x19cfab4`) when ACM does not say 1. On
  the SEP-less boot the ACM patches return success without writing the
  answer, so ACM reads 0 and AMFI disables. The byte stays off.
- It cannot be switched on later: the PPL toggle counts every call and panics
  (`enabling developer mode incorrectly`) on an enable that is not the first
  toggle of the boot.

**Fix.** `kernel amfi-developer-mode` (`KernelDeveloperModeResolver`) redirects
both disable calls in the decision to the matching enable (`BL
disable_developer_mode` -> `BL enable_developer_mode`, `BL` disable wrapper ->
enable wrapper `0x19d00a4`). Every toggle of the boot is then an enable: the
first sets the byte, later ones change nothing, so the panic condition is not
reachable. It refuses the kernel if any disable caller exists outside the
decision function. Part of the `kernel-codesign-invalid` opt-in: `boot-jit`
goes from 139 to 141 records on both iPad profiles.

With the PPL byte set, PPL's debug-entitlement gate would also pass on its
own; `ppl-debug-entitlements` stays as the narrower, independent guarantee.

**Not yet booted.** Watch for: a panic mentioning `enabling developer mode
incorrectly` (would mean an earlier toggle exists that this analysis missed);
otherwise retest a hardware breakpoint.

## Running it

As for 23H30, from the 26.7.2 IPSW and with a work directory of its own:

```sh
export WORK_DIR="$PWD/.liter8-ipad8-23H128"
B=.build/release/liter8
$B fw prepare --experimental --file /path/to/iPad_10.2_2020_26.7.2_23H128_Restore.ipsw
$B fw make-cfw --experimental
$B fw restore-cfw --experimental      # erase restore, wipes the iPad
```

The rest of the sequence is unchanged. Apple has to be signing 23H128 for
`restore-cfw`.
